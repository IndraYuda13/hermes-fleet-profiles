# Fleet Multi-Agent Orchestration, Governance & Defect Management

Comprehensive standard operating procedure for orchestrating specialized autonomous AI agent fleets (ORION, AURORA, FRAME, LENS, FORGE, ATLAS, PRISM, SENTINEL) across A2A pipelines, Kanban DAG dispatches, Impeccable design overhauls, and runtime defect rembukan.

## 1. Fleet Role Separation & Impeccable Ownership Matrix
| Fleet Role | Ownership Boundary | Impeccable Tools & Primary Deliverables | Execution Invariant |
|---|---|---|---|
| **ORION** | Chief of Staff, decomposition, governance, verdict synthesis | `routing`, `shape`, `craft-floor` review; Mission Contracts, Release Records | `orion_production_edits == 0` |
| **AURORA** | Product design authority, UI tokens, OKLCH color palettes | `init`, `concept-seed`, `palette`, `typeset`; `DESIGN.md`, `PRODUCT.md` | Design specs only; never implements code |
| **FRAME** | Frontend engineering, state machines, API integration | `typeset`, `layout`, `adapt`, `polish`; `styles.css`, `app.js`, HTML | Implements code; never self-certifies QA |
| **LENS** | Rendered visual/interaction QA & geometry verification | `audit`, `critique`, `contrast-rhythm`; `VISUAL_QA_REPORT.md`, viewport audits | Audits DOM; never edits production source |
| **FORGE** | Backend engineering, core business logic, worker daemons | APIs, SQLite queries, automation scripts | Backends & state machines |
| **ATLAS** | SRE, deployment, rollback anchors, process lifecycle | Systemd units, cgroup guards, rollback scripts | Infra stability & git anchors |
| **PRISM** | Functional QA, invariant assertions, test suites | Pytest suites, Playwright E2E tests | Strict test coverage; 0 false claims |

### Impeccable UI Invariants across Fleet
1. **Tabular Numeric Rule:** Always enforce `font-variant-numeric: tabular-nums` on prices, timers, nominals, and counters to prevent layout jitter during real-time polling.
2. **Glassmorphic GPU Isolation:** Pair `backdrop-filter: blur(20px)` with `contain: layout paint` and `transform: translateZ(0)` on navigation bars to prevent mobile compositing lag.
3. **Mobile Touch Safety Floor:** Interactive elements, buttons, category tiles, and form inputs must enforce a minimum 44×44px touch target geometry on mobile viewports (<=768px).
4. **Zero Horizontal Overflow:** Enforce `max-width: 100vw; overflow-x: hidden;` on body/root and verify across canonical viewports (320px, 360px, 390px, 768px, 1024px, 1440px).

## 2. A2A Communication & Timeout Management
- **Dual-Timeout Architecture:** Outbound client timeout in `config.yaml` (`a2a_agents.<peer>.timeout`) must strictly synchronize with inbound gateway deadline in `.env` (`A2A_REPLY_TIMEOUT`). Target: LENS/PRISM/SENTINEL/ORION: 1800s; FORGE/FRAME/AURORA: 1200s; ATLAS/RADAR/QUANT: 900s.
- **Progressive Decomposition:** Break large tasks into sequential multi-turn steps using `context_id` continuation (<300 words instruction per turn).
- **Concise Retry & Mechanical Fallback:** If a specialist times out, dispatch a concise 3-bullet retry. Split mechanical work (screenshot capture via FORGE) from judgment (visual audit via LENS).
- **Two-Way A2A Reverse Smoke Test Invariant:** Never assume bidirectional connectivity from outbound pings alone; verify the reverse direction (e.g. LENS -> ORION) using direct A2A JSON-RPC `SendMessage` calls.
- **Supervised Gateway Self-Restart Invariant:** Running agents are blocked by terminal guards from restarting their own gateway service directly. Request graceful restart via control socket or have the operator trigger it.
- **Evidence Manifest Git Revision Strategy:** Manifests committed inside git can NEVER contain their own commit SHA (avalanche effect). FRAME commits code (implementation SHA); all manifests reference that SHA; evidence artifacts are committed in a separate evidence commit.
- **Serial Incremental SDLC Invariant:** When mandated to work step-by-step ("1 per 1 dikerjakan, di-test, di-verifikasi"), tag initial state (`vX-baseline`), decompose into separate Kanban cycles (FORGE/FRAME -> PRISM/ATLAS -> commit/tag), and never batch multiple improvements into a single monolithic commit.
- **Remote MCP & Ad Monetization Engine:** See `references/ad-network-and-mcp-monetag.md` for OAuth 2.1 PKCE flow, Monetag MCP setup, and Service Worker push ad integration runbooks.

## 3. Defect Remediation Flow (Collaborative Rembukan)
- **Zero-Solo Invariant:** When runtime defects or upstream policy limits occur, ORION must never resolve them alone.
  1. *Discover & Isolate:* Trace logs and pin failure mechanisms.
  2. *Fleet Briefing:* Broadcast structured problem briefing via `a2a_orchestrate(capability="*")`.
  3. *Kanban DAG Dispatch:* Create discrete cards for logic (FORGE), UI (FRAME), infra (ATLAS), and QA (PRISM/LENS).
  4. *Independent Verification:* Implementer submits evidence; verifier confirms invariant pass before closure.
- **Kanban Task Creation & CLI Fallback:** For reading, commenting, and updating tasks, use native `kanban_show`, `kanban_comment`, and `kanban_list`. For task creation: if the native `kanban_create` tool encounters parameter signature mismatches (e.g. `missing required positional argument: 'title'`), use the deterministic Hermes CLI directly:
  `/usr/local/lib/hermes-agent/venv/bin/hermes kanban create --tenant "<TENANT>" --assignee "<ASSIGNEE>" --priority <PRIORITY> [--parent "<PARENT_ID>"] --workspace "dir:<PATH>" --body "<BODY>" --json "<TITLE>"`
  Always include `--json` for structured JSON output and verifiable task ID parsing.
- **Kanban Live Claim Guard & Forced Completion (`--force`):** When reviewing or completing a task that is claimed or active under another worker run, `kanban_complete` without worker ownership credentials will fail-closed (`kanban_complete refused: task is running under a live worker claim`). When closing or overriding from an orchestrator/operator session after independent verification, pass `force: true` or run `/usr/local/lib/hermes-agent/venv/bin/hermes kanban complete --force <task_id>`.
- **Skill Manifest Pre-Validation & Bootstrap Crash Recovery Invariant:** When specifying `skills: [...]` during task creation, verify each skill name exists in the target assignee profile's installed skill list. Pinning an unavailable or mistyped skill causes the dispatched worker to crash instantly at bootstrap (`Error: Unknown skill(s)`). Because card skill lists are immutable across retries, all automatic dispatcher attempts will fail identically before running code. Prefer empty `skills: []` to inherit the profile's configured defaults unless an explicitly verified specialist skill is required.
  - *Immediate Supersession on Bootstrap Crash:* When a task crashes with `Error: Unknown skill(s)` or `Unknown toolset(s)`, do not wait for the dispatcher to exhaust retries or mistake the crash for a QA/code failure. Because card attributes (including skill pins) are immutable on existing tasks, retries cannot recover. Immediately comment on the broken card explaining the bootstrap failure and spawn a replacement task with `skills: []` targeting the identical revision and acceptance criteria.
  - *Downstream Child Task Skill Sanitation:* When implementers (`forge`, `frame`) spawn downstream verifier cards (`prism`, `sentinel`), they frequently hallucinate procedural skills (e.g. `change-impact-verification` or category-prefixed paths). Verifier cards created for downstream verification must always use `skills: []` to rely on the verifier profile's built-in toolset and default prompt instructions.
- **Shared Worktree Serialization Invariant (`workspace_kind: "dir"`):** When multiple remediation tasks target the same shared repository directory (`workspace_kind: "dir"`), do not dispatch them concurrently. Concurrent workers sharing a single working tree risk dirty staging collisions, git index locks, and active data file pollution (e.g. test runs overwriting shared caches). Sequence parallel findings via parent dependency gating (`parents: ["<prior_task_id>"]`) so each subsequent remediation builds strictly on top of the preceding sealed commit.
- **Single-Writer Arbitration for Verifier-Spawned Tasks:** Independent verifiers (PRISM, SENTINEL) routinely generate child remediation cards upon discovering defects. When multiple verifier cards or orchestrator cards target the same scope or assignee in a shared worktree, ORION must actively arbitrate: designate one primary card as the sole writer, convert redundant or overlapping tasks into read-only evidence suppliers via comments, and instruct workers not to stage or commit source files concurrently.
- **Active Runtime State Hash Invariant & Test Isolation:** Verification gates and test reproduction scripts executed in shared workspaces must strictly isolate runtime data (e.g. using temporary `DATA_DIR`, ephemeral databases, or `*_PERSIST=false` flags). Verifiers must record SHA-256 hashes of persistent state files (such as `data/session_pool.json` and `data/credentials.json`) before and after test execution. Any unintended hash mutation is an immediate release blocker (`active_runtime_data_mutated`), even if all functional assertions pass.
  - *Test Harness Singleton/Persistence Isolation:* Repositories with file-backed persistence must enforce isolation at the root test harness (`conftest.py` or base fixture) using an isolated temporary directory and disabling persistence by default. Relying on external env flags or nested subprocess tests is insufficient because direct/bare `pytest` imports application singletons that bind to repository data paths.
  - *Attribution of Runtime Mutations:* Before assuming an active data mutation originated from live service traffic, inspect the file modification timestamp against service uptime and hash string literals against test fixtures. Test-driven fixture writes typically leave recognizable test strings and occur during test execution windows while the service is dead.
  - *Authorized Runtime State Disposition:* When resetting test-polluted state, never overwrite or delete with assumed `{}` or `[]`. Archive the exact existing bytes to a root-restricted directory (`0700` dir, `0600` archive/manifest) with matching SHA-256 hashes. Generate the replacement baseline using the application's actual reader/writer logic in a disposable path, verify it parses as empty, and atomically install it.
  - *Active-Service Probe vs In-Memory Cache Cleanliness:* When functional verification requires probing an already-active service daemon on loopback, live requests necessarily touch the daemon's in-memory session cache. Verifiers can verify persistent file immutability (unchanged SHA-256 of state files on disk), but cannot truthfully claim zero in-memory cache mutation. Verifiers must mark in-memory cache cleanliness as `UNVERIFIED` rather than failing the gate or asserting an unsupported clean state. If strict in-memory cache isolation is required, test against a disposable child daemon on a separate test port with persistence disabled.
- **Ephemeral Test Process Disambiguation & Mandatory Teardown Invariant:** When verifiers (PRISM, SENTINEL) execute live HTTP or client smoke tests against an isolated candidate, they may launch temporary background listener processes (e.g. `uvicorn` on loopback port 8560).
  - *Provenance Disambiguation:* An active listener found via `ss -ltnp` must not be blindly assumed to be the installed systemd service or an unauthorized deployment. Check process ownership and lineage (`ps -o pid,ppid,user,args -p <PID>` and `systemctl show <service> --property=MainPID,ActiveState`).
  - *Mandatory Teardown Before Task Completion:* Ephemeral test processes must be terminated before completing the verification task. The verifier must verify and report port closure (`ss -ltnp` empty for the port), prove the systemd unit remained `inactive`, and ensure active persistent state hashes are unchanged.
- **Staged Systemd Hardening & Offline Verification Invariant:** When proposing least-privilege systemd units (migrating from root to a dedicated unprivileged user, read-only `/opt` source, protected `/etc` config, `/var/lib` StateDirectory, `NoNewPrivileges`, namespace isolation, and syscall filters):
  - Propose unit files inside repository source (e.g. `systemd/<service>.service`) and document rollout/rollback in `docs/`.
  - Statically verify offline using `systemd-analyze verify <path>` and `systemd-analyze security --offline=yes <path>` to demonstrate exposure reduction without touching `/etc/systemd/system/`, reloading daemons, or starting the service.
  - *Decoupled Pre-Activation Verdicts:* Keep deployment and activation strictly decoupled from source review. For services requiring unprovisioned accounts/directories, verifiers must issue decoupled verdicts: `Source & Staged Hardening Candidate: ACCEPTABLE (for future window)`, but `Runtime Activation: BLOCKED` pending explicit host provisioning (dedicated user/group, `/opt` snapshot, protected `/etc` config, `/var/lib` state directory) and an activation-window smoke/retest at the exact same SHA.
  - *Authorized Activation Window & Fail-Closed Rollback Invariant:* After independent gates pass with decoupled verdicts (source acceptable, activation blocked):
    1. *Human Authorization Gate:* ORION must never trigger host mutation or service activation autonomously. Present an explicit authorization checkpoint defining the exact scope (non-root account provisioning, `/opt` source snapshot, protected `/etc` config, `/var/lib` StateDirectory, unit installation, daemon reload, loopback start, native smoke/retest, rollback plan).
    2. *Dedicated Host Mutation Dispatch (ATLAS):* Dispatch host changes as a single dedicated task to ATLAS with frozen interfaces: exact source SHA, staged unit path, baseline unit hash, and persistent state file hashes.
    3. *Zero-Secret File Placement:* Never copy secrets or place uninspected credentials into `/etc/`. Apply least-privilege modes (`0750` for dirs, `0600` for config/credentials, `0700` for StateDirectory).
    4. *Deterministic Native Smoke & Same-SHA Retest:* Immediately verify runtime identity is non-root (`User != root`), listener is strictly loopback, systemd is active, health/models/native client smoke (`hermes -p <profile> -z`) passes against loopback, and active data hashes remain unchanged.
    5. *Atomic Fail-Closed Rollback:* If any prerequisite, start, smoke, non-root check, or retest fails, immediately stop the service, restore baseline unit from recorded backup, daemon-reload, prove port closed, and report `ROLLED BACK / BLOCKED`. Never leave a half-provisioned or failing service running.
- **Native Client Smoke Classification (Sanitized Upstream Errors vs Functional Regression):** When running native client smoke tests (e.g. `hermes -p testing -z`) against an isolated gateway candidate:
  - *Sanitized Error Interception:* If the gateway correctly intercepts internal failures and returns sanitized public errors (`{"error": "Internal server error"}`), client tools will exit with an error. Verifiers must NOT falsely pass this as a successful client interaction.
  - *Root Cause Classification:* Distinguish whether the sanitized error is expected due to intentional absence of upstream credentials/network in the isolated test sandbox (in which case the native live smoke is `BLOCKED / NOT VERIFIABLE`, but sanitized error handling is `VERIFIED`), or an internal gateway routing/delimiter defect. Never substitute sanitized error responses for functional upstream pass evidence.
- **Test-Contract vs Implementation Defect Disambiguation on Intentional Reset Invariants:**
  - When verifiers (PRISM) report failures in live multi-turn continuity or regression suites (e.g. `CG_RUN_LIVE_TESTS=1 pytest`):
    1. *Inspect Contract Invariants First:* Check whether the failure stems from an intentional security/isolation contract (e.g. forcing session reset to root when a turn request carries an explicit session ID but omits prior assistant history, preventing cross-turn context or credential leakage).
    2. *Test-Contract Classification:* If runtime logic correctly enforces fail-closed isolation while the legacy test expected stateful carryover without history, classify this as a **test-contract defect** (`tests/`), not an application regression.
    3. *Release Gate Discipline:* Do NOT declare a release "stable" or unconditionally released while an optional or live test suite is failing. Report: "operational for normal use, but formal release gate remains BLOCKED / NOT RELEASED pending test-contract repair."
    4. *Promote Scoped Remediation:* Do not duplicate cards. Promote the already-scoped test repair task (e.g. to FORGE) with explicit requirements: update the test to pass proper full-history continuation, and assert a separate regression proving no-history requests reset cleanly.
- **Verifier-Remediation Dependency Inversion Trap (Deadlock Prevention):**
  - When an independent verifier (`PRISM`, `SENTINEL`) identifies a defect and generates or links a child remediation card (`FORGE`, `FRAME`):
    1. *No Indefinite Block Loop:* A verifier card's contract is to **render a definitive, evidence-backed verdict** (PASS or FAIL), not to wait until code is fixed. When defects are confirmed and child remediation is scoped, the verifier must NOT block indefinitely or wait in a loop. It must complete with an explicit verdict: `NOT RELEASED / FAIL pending <remediation_task_id>`. This completes the verifier run legitimately, allowing child remediation tasks that list the verifier as a parent to promote from `todo` to `ready`.
    2. *No Parent-Gating by Incomplete Verifier:* The remediation card must NEVER declare `parents: ["<failing_verifier_task_id>"]` unless the failing verifier is ready to complete with its FAIL verdict. If the verifier remains in `blocked` or `triage`, the child remains stuck in `todo (dependency_wait)`.
    3. *Orchestrator DAG Remediation:* If a dependency cycle occurs, ORION must immediately detach the failing verifier from the remediation card's parents (`kanban_link` / parent removal) or instruct the verifier to close with a non-release finding, promoting the remediation card to `ready` immediately.
    4. *Discrete Retest Task:* Once the remediation commit is sealed, commission a **fresh independent verifier task** targeting that exact new SHA. Do not attempt to resurrect or coerce the historical verifier card to pass.
- **Mid-Flight Scope & Policy Reconciliation for Independent Verifiers:**
  - When the operator or user alters capability or security requirements mid-turn (e.g. expanding an allowlisted profile from a minimal 6-tool subset to 12 full capabilities including terminal/browser/delegation):
    1. *Fail-Closed Verifier Invariant:* Independent verifiers enforce strict specification fidelity. If the original task card body contains restrictive negative assertions ("demonstrate no terminal/file/browser reaches profile"), the verifier will report `BLOCKED: contradictory acceptance criteria` rather than guessing whether a subsequent comment supersedes the task body.
    2. *Formal Policy Reconciliation Posting:* ORION must post a **Formal Policy Reconciliation** comment to the verifier's task thread: explicitly declaring the user's directive authoritative, identifying the superseded task-body clauses, and defining the exact new required and forbidden sets.
    3. *Unblock & Re-Evaluate:* After posting the formal reconciliation, unblock the verifier task (`kanban_unblock`) so the verifier can certify the implementation against the authoritative reconciled criteria.
    4. *Goal-Judge Stale-Body Trap on Reconciled Tasks:* In tasks dispatched with `goal_mode: true`, the auxiliary goal judge checks completion against the card's `title` and `body`, ignoring subsequent thread comments. If criteria expand mid-flight, a verifier's evidence-backed completion will be rejected by the goal judge, triggering `block_loop_detected` -> `triage`. Orchestrators must recognize this as an administrative artifact rather than a code defect: either update the card via specification if available, or administratively complete with `--force` / record final disposition to stop unblock loops.
- **Automatic Kanban Blocker Triage & Dependency Advancement Invariant:**
  - When receiving automatic status notifications (`[kanban] Task <id> blocked; needs attention`):
    - Never treat the alert as a prompt to re-decompose the mission or create duplicate task graphs.
    - Inspect the blocked card via `kanban_show`. Check whether it is an upstream verifier blocked on a defect for which it already created a child remediation task.
    - If the verifier is blocked because acceptance criteria failed, record the formal closing verdict on the parent card via `kanban_comment` (`NOT RELEASED pending <child_task_id>`) and unblock/complete the card so the dependency tree can advance the child task.
  - *Single Active Remediation Card on Review Rejection:* When a review returns a task with `changes_requested`, the task automatically returns to `ready`/`running` for the original implementer. Never spawn a duplicate remediation card. Maintain work strictly on the existing card. If a duplicate card is accidentally created, immediately cancel or force-complete it without mutations to maintain single-writer serialization on the shared repository.
  - *Review-Rejection & Worker Timeout Notification Discipline:* Automatic Kanban notifications for `review requested changes (BLOCK)` and `timed out; dispatcher will retry` are state confirmations, not prompts to re-decompose tasks or generate sibling cards. Review rejections return the existing task directly to the implementer (`changes_requested` -> `ready`/`running`); timeouts trigger automated retry runs by the dispatcher with workspace files preserved. Never treat rejection alerts as approvals, never create duplicate cards, and do not interrupt automated retries.
- **Pre-Commit Clean Diff & EOL Verification Invariant (`git diff --check` & `py_compile`):** Before committing or staging candidate fixes in a shared repository, always run `git diff --check`. Mixed CRLF/LF line endings or trailing whitespace introduced by targeted find-and-replace edits must be resolved with base-consistent EOL. When normalizing EOL or re-applying patches, verify that find-and-replace anchors did not miss targets due to line-ending mismatches (leaving variables or definitions uninitialized). Always run `python3 -m py_compile <files>` and confirm successful compilation before running test suites.
- **Post-Seal Parent Commit Diff-Check & Serial DAG Correction:** When an implementer seals a commit and claims completion, ORION must independently run `git diff --check <parent_sha> <sealed_sha>`. If commit-level defects (such as CRLF line endings, trailing whitespace, or unformatted code) are introduced:
  - Do not inject ad-hoc fixes into the shared worktree while a subsequent worker is already actively running.
  - Insert a discrete serial normalization task into the Kanban DAG directly following the active writer and gating subsequent downstream work.
  - Reparent affected downstream tasks via `kanban_link` to depend on the normalization task.
  - Instruct downstream verifiers (PRISM, SENTINEL) that the defective intermediate SHA is rejected as a clean release candidate and that release verification must bind exclusively to the consolidated post-normalization commit.
- **Worker Timeout Handling & Progress Preservation Invariant:** When a worker card times out (`elapsed > limit`), the dispatcher automatically schedules a retry run. A timeout is NOT a bootstrap crash (`Unknown skill`); the shared worktree retains the worker's in-progress source and test files. The orchestrator and retry worker must NOT discard partial progress or restart exploration from scratch. Immediately check `git diff --check`, compile modified files (`python3 -m py_compile`), and resume from the latest verified state toward sealing.
- **Strict Protocol Hardening vs Custom Framing Delimiter Preservation:** When hardening parsers to enforce strict per-turn capability binding against foreign/replayed tokens (e.g. `<<<TOOL_CALL_<nonce>>>`), restrict suppression specifically to reserved protocol tokens. Do not blanket-suppress arbitrary user or test custom framing delimiters (e.g. `<<<START>>>` / `<<<END>>>`); verify that neighboring fragmented and non-protocol delimiter contracts remain functional.
- **Strict Anti-Polling Invariant & Native Event-Driven Session Wake:**
  - *Zero Busy-Wait & Autonomous Self-Discipline:* ORION must NEVER run sleep-and-check polling loops in terminal (`sleep 30` -> `kanban_show` -> `sleep 30`, or bash `while` loops) while awaiting background worker completion. Polling wastes tool calls, burns foreground timeouts (600s), blocks user interaction, and violates reactive architecture. Crucially, ORION must NEVER ask the user to remind it not to poll ("ingetin gua ya bre"); self-discipline is maintained autonomously via skills.
  - *Hermes Core Native Wake Architecture (No Third-Party Plugins):* Do not install or rely on third-party `self-wake` plugins. Hermes Agent core already features native session wake (`gateway/wake.py` and `delivery_mode="notify+wake"`).
  - *CLI Fallback Subscription Registration Invariant:* When creating a task via the Hermes CLI fallback (`hermes kanban create`), the CLI subprocess does not inherit the ambient gateway session ContextVar, so `kanban_notify_subs` is not automatically populated. ORION MUST immediately register the subscription explicitly:
    `/usr/local/lib/hermes-agent/venv/bin/hermes kanban notify-subscribe --platform <PLATFORM> --chat-id "<CHAT_ID>" --chat-type <CHAT_TYPE> --notifier-profile <PROFILE> --delivery-mode notify+wake <TASK_ID>`
    (e.g., `--platform telegram --chat-id "696907598" --chat-type dm --notifier-profile orion --delivery-mode notify+wake <TASK_ID>`).
  - *Mandatory Turn Release:* After dispatching Kanban tasks and ensuring active `notify+wake` subscription, ORION MUST report the dispatch status clearly and conclude the turn immediately. Do not hang the session waiting. The live gateway will natively wake ORION's session the exact second the worker reaches a terminal event (`completed`, `review_requested`, or `blocked`), injecting the event payload into the conversation turn.
- **Consolidated Release Candidate Parent-Gating Invariant:**
  - Verifier tasks (`PRISM`, `SENTINEL`) that gate release decisions must NEVER be scheduled or dispatched against intermediate remediation commits while upstream remediation tasks are still active or queued.
  - Independent verifier cards must strictly declare `parents: ["<terminal_remediation_task_id>"]` to remain in `todo` until the final consolidated candidate SHA is sealed.
  - If DAG adjustments (such as EOL normalization or secondary defect fixes) insert intermediate cards, ORION must immediately call `kanban_link(parent_id="<new_predecessor>", child_id="<verifier_task_id>")` so verifiers do not prematurely execute against stale or defective predecessor commits.
- **Mid-Turn Progress Synthesis Architecture:**
  - When the user requests a status or progress update during a complex multi-stage pipeline ("progressnya udah sampai mana?"), ORION must avoid raw task ID lists or verbose log dumps. Provide a structured 4-tier brief:
    1. *Completed & Sealed:* Specific capabilities/defects resolved, verified, and sealed with commit SHAs.
    2. *Actively In-Flight:* The exact scope and files the active single-writer worker is executing right now.
    3. *Remaining Path to Release:* The explicit sequential checklist remaining before activation (subsequent fixes, clean diff normalization, dual independent verification, authorized provisioning, runtime smoke).
    4. *Containment & Current State:* Verifiable runtime safety metrics (exact HEAD SHA, service inactive status, bound port closure, persistent state SHA-256 hashes).

## 6. Asynchronous Dual-Verifier Arrival & Release State Machine
- **Asynchronous Verifier Arrival Handling:** When independent verifiers run in parallel (e.g. LENS visual QA and PRISM functional/a11y QA), one verifier will inevitably finish and report first via A2A or Kanban.
  1. *Early Arrival Acknowledgment:* Acknowledge receipt, inspect on-disk artifacts (`LENS_REVIEW_REPORT.json` or PRISM test logs), and approve promotion to `BEST_BUILD_SHA` for that verification dimension.
  2. *Strict In-Flight Guard:* Record `INTERNAL_VISUAL_GATE = PASS` (or functional pass), but keep `MISSION_RELEASE_STATE = IN_VERIFICATION` while sibling verifier tasks remain active (`status: running`). Never declare mission release or notify the human owner until ALL required verifier tasks reach terminal states.
  3. *Owner Acceptance Reservation:* `INTERNAL_RELEASE_GATE = PASS` marks internal verification closure only. `OWNER_VISUAL_ACCEPTANCE` and `OWNER_ACCEPTANCE` MUST remain `PENDING`. Internal agents (ORION, LENS, PRISM, FRAME) are strictly forbidden from setting owner acceptance to `PASS`; only the human owner can transition it.
  4. *Unified Meta-Release Synthesis:* Once all verifiers complete with PASS, ORION synthesizes the unified release decision record, bundles all visual and functional evidence, and presents the deliverable with `MISSION_RELEASE_STATE = AWAITING_OWNER`.

## 7. Declarative Fleet Upgrades, Gateway Lifecycle & Terminal Safety
- **HERMES_HOME Subprocess Scope Trap:** When running deployment or bootstrap scripts from inside an active profile session (such as `orion`), `$HERMES_HOME` is exported in the environment as `/root/.hermes/profiles/<profile_name>`. Scripts defaulting to `${HERMES_HOME:-$HOME/.hermes}` will mistakenly target the subprofile directory, polluting it with nested `profiles/` directories. Always explicitly prepend `HERMES_HOME="${HOME}/.hermes"` when invoking root fleet scripts or bootstrap tools from an active agent session.
- **Terminal Guard Lifecycle Choke Point & Sibling Gateway Restarts:** Running `systemctl --user restart hermes-gateway-<profile>.service` directly is blocked by Hermes's terminal lifecycle guard (`contains_gateway_lifecycle_command`), which matches `hermes-gateway` and `systemctl.*restart`. To restart sibling gateways safely without triggering the terminal guard, use the profile-flag CLI form: `hermes -p <sibling_profile> gateway restart`. The lifecycle guard explicitly permits restarting sibling profiles (`_named_profile_is_current` check allows sibling operations while blocking restarts of the executing profile). Never forcefully restart one's own current gateway profile mid-turn, as SIGTERM terminates the active child process before delivering the response.
- **Declarative Git Pulls vs Runtime Secret Preservation:** Git pulls from declarative configuration repositories (`hermes-fleet-profiles`) contain sanitized placeholders (`${MONETAG_API_TOKEN}`). Never use `--replace-config` blindly on live environments. Deploy declarative assets (`SOUL.md`, `profile.yaml`, custom/global skills) first, then surgically update targeted non-secret delta keys (e.g. `skills.disabled`) while preserving secrets byte-for-byte.
- **Fleet Model Re-Routing & Verification Invariant:** When changing default inference models across fleet profiles:
  1. *Verify Active Endpoints:* Query the local router/gateway first (`curl -s http://localhost:20128/v1/models | jq -r '.data[].id'`) to verify exact upstream model IDs (`gpt-sol`, `gpt-terra`, `ag-opus-pool`) before applying.
  2. *Surgical Per-Profile Update:* Use `hermes -p <profile> config set model.default <model_id>` to ensure atomic YAML updates without formatting corruption.
  3. *Audit State Before Restart:* Run `hermes profile list` to verify that each profile's model column matches the intended role-model topology.
  4. *Gateway Restart Guard:* Never attempt `hermes gateway restart --all` or restart the executing profile from within an active session—it is blocked fail-closed by Hermes terminal guards. Either delegate the restart to the human operator outside the gateway or restart sibling profiles individually via `hermes -p <sibling> gateway restart`.
- **Multi-Surface Profile Capability Expansion & Platform Boundary Invariant:**
  - When the operator expands a profile's toolset (e.g. granting `terminal`, `file`, `browser`, `code_execution`, `web`, `delegation` across all execution contexts):
    1. *Apply Across All Callable Surfaces:* Use official Hermes CLI commands (`hermes --profile <name> config set ...`) to configure the exact authorized list across global `toolsets`, `platform_toolsets.cli`, `platform_toolsets.telegram`, and `platform_toolsets.a2a`. Never edit YAML files directly.
    2. *Strict Boundary Isolation:* Expanding functional toolsets must NEVER weaken platform authorization boundaries. Telegram user allowlists must remain strictly pinned to numeric owner ID (`TELEGRAM_ALLOWED_USERS="<id>"`), maintain `allowed_chats: ["__dm_only__"]`, `group_policy: disabled`, and `guest_mode: false`.
- **Mixed Sys.Modules & In-Memory Daemon Drift Post-Update:** Running `hermes update` modifies CLI libraries on disk but does not restart active background gateway daemons. In-flight daemon workers continue executing pre-update modules in memory (`mixed sys.modules`), producing subtle runtime mismatches between CLI behavior and daemon tool invocation. Before certifying declarative synchronization or runtime upgrades, verify gateway uptime and schedule sibling gateway restarts (`hermes -p <profile> gateway restart`) or operator-level gateway restart.

## 8. Bi-Directional Fleet Profile Synchronization & Remote Backup (hermes-fleet-profiles)
When auditing or persisting live fleet policy, SOUL.md updates, custom skills, or model changes back to the version-controlled fleet repository (`/root/projects/hermes-fleet-profiles` -> `IndraYuda13/hermes-fleet-profiles.git`):
1. **Two-Layer Fleet Backup Verification (Git Remote vs Live Runtime Drift):**
   - *Zero False-Backup Invariant:* Never claim the fleet is fully backed up based solely on `git status` (clean worktree) and `HEAD == origin/main`. Git only tracks files already synchronized into the repository working tree.
   - *Layer 1 (Git Remote Parity):* Run `git fetch && git status -sb` and verify ahead/behind count between `HEAD` and `origin/main`.
   - *Layer 2 (Live Runtime Drift Probe):* Execute `HERMES_HOME=/root/.hermes bash scripts/sync.sh` (dry-run) to detect un-synced runtime mutations across `/root/.hermes/profiles/*`.
   - *Layer 3 (Destructive Deletion Accounting & Curator Disambiguation):* Parse proposed change lines (specifically deletions vs additions/modifications). When mass skill deletions appear in a dry-run (`*deleting profiles/<name>/skills/...`):
     - *Repo Deletion vs Fleet Loss Distinction:* A dry-run deletion means the repo contains files *no longer present on the live profile disk*. It is not `sync.sh` deleting live files.
     - *Curator Umbrella Consolidation Audit:* Check the profile curator ledger (`hermes -p <profile> curator ledger --limit 30`) and status (`hermes -p <profile> curator status`). Determine whether removed skills were intentionally absorbed into class-level umbrellas (e.g. `domain-ux-architecture` on AURORA, `software-development-workflows` on FORGE/PRISM, `fleet-orchestration-suite` on ORION, `service-api-verification` on PRISM).
     - *Global vs Profile Inheritance Verification:* When profile copies of global skills are pruned, do not assume profile inheritance is automatic. Always verify active availability with `hermes -p <profile> skills list --source all --enabled-only`.
   - *Layer 4 (Snapshot Recovery Provenance):* Verify recent timestamped snapshots exist in `/root/projects/hermes-fleet-backups/` before performing any apply or remote push.
2. **Curator Runtime Artifact & Telemetry Hygiene:**
   - *Rsync Staging Exclusions:* Sync tooling must strictly exclude ephemeral runtime directories (`--exclude='.curator_backups/' --exclude='.locks/'`) during rsync to avoid staging megabytes of local backup tarballs and lockfiles into the git working tree.
   - *Telemetry vs Declarative Versioning:* Dynamic curator state files (`.curator_state`, `.curator_suppressed`, `.usage.json`, `.bundled_manifest`) churn continuously due to background telemetry and usage counters. Keep git focused on declarative policies (`config.yaml`, `SOUL.md`, `profile.yaml`, `SKILL.md`) to prevent noisy, non-functional commit churn.
3. **Operational vs Declarative Config Delta Audit:**
   - Deep-diff all modified `config.yaml` files before staging.
   - Distinguish benign schema bumps (e.g. `_config_version: 44 -> 45`, registered builtin toolset lists) from high-impact operational changes (e.g. enabling messaging platforms `platforms.whatsapp.enabled: true`, open group access policies, modified bridge ports, or disabled plugins). Treat operational platform mutations as explicit deployment decisions requiring separate review, not incidental backup diffs.
4. **Model & Role Topology Alignment:**
   - The validation engine (`scripts/validate_fleet.py`) enforces that `profiles/<name>/config.yaml` model defaults match `governance/roles.yaml`.
   - If profile models change (e.g. migrating Sol/Terra/Opus allocations), update `governance/roles.yaml` to match before running validation.
5. **Declarative Synchronization Execution:**
   - Always run with root Hermes home: `HERMES_HOME=/root/.hermes bash scripts/sync.sh` (dry run inspection) followed by `HERMES_HOME=/root/.hermes bash scripts/sync.sh --apply`.
   - `sync.sh --apply` automatically stages declarative changes into `profiles/` and `global/skills/`, creating an immutable timestamped snapshot in `/root/projects/hermes-fleet-backups/YYYYMMDDTHHMMSSZ`.
6. **Fleet Policy Validation & Clean Diff Gates:**
   - Execute `python3 scripts/validate_fleet.py --repo-root /root/projects/hermes-fleet-profiles`.
   - All role toolsets, model parity checks, and SOUL invariants must return `Fleet policy: PASS`.
   - *Pre-Commit Whitespace & Formatting Gate (`git diff --check`):* Always run `git diff --check` after `sync.sh --apply`. Trailing whitespace or blank lines at EOF must never be committed. Crucially, remediate formatting defects in the live source files under `/root/.hermes/profiles/` first—never patch only the repository copy, as subsequent sync runs will overwrite repo-only fixes or recreate drift. Re-run `sync.sh --apply` after live remediation.
   - *Secret Pattern Scan Scoping & Documentation False Positives:* Run regex checks over git additions (`git diff -U0 ... | grep '^\+'`) for credential tokens (`ghp_`, `sk-`, `PMAK-`, private keys) to ensure sanitizers operated fail-closed before staging. Do not run broad context-inclusive diff greps over markdown documentation discussing token formats or diagnostic file references (e.g. `delegate-task-concurrency-diagnosis.md`), which cause false-positive secret alarms.
   - *Tracked Parity Verification & Post-Sync Drift Resolution:* Compare tracked repository files against sanitized live profile contents (`tracked_declarative_parity`) to ensure 0 parity mismatches. Because active profile gateways continue processing tasks and updating telemetry or skills mid-flight, verify whether drift occurred between initial sync and seal. If declarative files drifted, sync the exact drifted files into the worktree, verify byte identity (`cmp`) and `git diff --check`, and ensure all tracked declarative files match live disk before committing.
   - *Point-in-Time Capture Gate for Runtime Telemetry:* Mutating telemetry files (`.usage.json`, curator states, session logs, dynamic counters) continuously change while fleet agents are active. Requiring live-current exact byte parity (`cmp`) across multiple turns or async review cycles creates an infinite rejection loop. For live-mutating telemetry files, enforce a **point-in-time capture gate**: the worker records the UTC capture timestamp and the matching source/destination SHA-256 hash immediately upon copying. Subsequent review and commit gates must validate the repository copy against this recorded capture fingerprint and schema/whitespace checks, rather than requiring live runtime telemetry to remain frozen after capture.
   - *Live-Authoritative Policy Reconciliation Gate:* When syncing a fleet backup where the live fleet is designated the authoritative source of truth, repository validation (`validate_fleet.py`) may fail if live configurations contain toolsets or capabilities not yet enumerated in `governance/roles.yaml` (e.g. `ERROR: <profile>: platform tools outside policy: [...]`). In this state, do NOT alter or sanitize away the live configuration to appease the validator. Reconcile the policy manifest (`governance/roles.yaml`) by adding the live-authorized capability to the specific scope (e.g. `allowed_platform_toolsets` vs `allowed_root_toolsets`), re-render via `python3 scripts/apply_role_policy.py`, and re-run validation until `Fleet policy: PASS`. Policy must codify verified live architecture, not truncate it.
7. **Git Commit & Remote Push:**
   - Check `git status`, add all synced declarative updates, author a descriptive commit, and push upstream to `origin main`.
   - Ensure user project working branches (e.g. `digiflazz-topup-bot`) are also pushed to their respective remotes.

## 9. Full-Stack Fleet Bootstrapping Pipeline (PRD to Production Release)
When bootstrapping a greenfield full-stack product from a formal PRD:
1. **Workspace & Baseline Ratification:**
   - Initialize `/root/projects/<app_name>` git repository.
   - Commit the ratified PRD to `docs/PRD.md` as the inviolable baseline before authoring code.
2. **Canonical 6-Layer Dependency DAG:**
   - **Layer 1 (Parallel Architecture & Tokens, Priority 100):**
     - `AURORA`: Visual Design System, Design Tokens, Editorial Style, Anti-AI Slop UI contract (`docs/DESIGN_SYSTEM.md`).
     - `FORGE`: PostgreSQL schema (Drizzle ORM), atomic inventory reservation, immutable wallet ledger, payment gateway client & background worker sweeps.
   - **Layer 2 (Frontend Implementation, Priority 90):**
     - `FRAME`: Storefront, bottom-sheet cart, dynamic input view, QRIS payment screen with 1-tap save, customer dashboard, admin portal. Parents: `AURORA` + `FORGE`.
   - **Layer 3 (Runtime & Infrastructure, Priority 80):**
     - `ATLAS`: DB provisioning, background worker daemon (systemd), ingress reverse proxy (Nginx / Cloudflare Tunnel) with SSL/TLS, health check. Parent: `FRAME`.
   - **Layer 4 (Independent Dual-QA Gate, Priority 70):**
     - `PRISM`: Concurrency race testing (anti-overselling), webhook idempotency, late-payment ledger reconciliation, wallet boundary checks. Parent: `ATLAS`.
     - `LENS`: Rendered visual QA across 360px/390px/412px viewports, anti-slop compliance, 0px horizontal overflow, touch target geometry (>=44px). Parent: `ATLAS`.
   - **Layer 5 (Security Audit, Priority 65):**
     - `SENTINEL`: RBAC boundary verification (Owner vs Admin/Support financial mutations), IDOR on invoice attachments, secret sanitization. Parents: `PRISM` + `LENS`.
   - **Layer 6 (Production Release & Synthesis, Priority 50):**
     - `ORION`: Verification synthesis, Definition of Done compliance audit, operational handoff. Parent: `SENTINEL`.
3. **Concurrency Sequence Invariant (Postgres Advisory Locks):**
   - In high-concurrency checkout races, autoincrement sequence counters or non-locked queries for human-readable order/invoice numbers (e.g. `ORD-YYYYMMDD-XXXX`) collide or abort under row contention.
   - Serialize sequence generation inside transactions using PostgreSQL transaction-scoped advisory locks (`SELECT pg_advisory_xact_lock(hashtext('order_seq_lock'))`) so concurrent checkouts serialize cleanly without deadlocks or sequence gaps.
4. **Defect Disposition Ledger & Conditional Staged Release:**
   - When independent verifiers (SENTINEL, LENS) surface material P0/P1 defects (e.g. missing session auth on admin APIs, attachment BOLA/IDOR, WCAG contrast violations) alongside verified core business logic:
     - Do not declare unconditional production release.
     - Do not halt the entire project if public read-only discovery is functional and secure.
     - Author an explicit **Defect Disposition Ledger** mapping each defect to its owning specialist (`FORGE` for security/API, `FRAME` for UI/WCAG), severity (`P0/P1/P2`), exact reproduction tests, and target files.
     - Issue a **Conditional Staged Release (Restricted Beta)**: public catalog/browsing approved on live ingress, while checkout, payment processing, and admin mutations remain gated until the remediation sprint completes.
