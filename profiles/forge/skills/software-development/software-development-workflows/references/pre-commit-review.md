# Pre-commit review reference

Review the actual diff and its surrounding call sites before committing. Check correctness, trust boundaries, error paths, public contracts, test coverage, and unintended generated/debug/secrets changes. Run the focused tests and configured lint/type checks. Report findings by severity with file/line evidence; distinguish blocking defects from optional cleanup.

For a pull request, read the metadata and changed-file list before the diff, check out the exact head when practical, and post only findings that remain valid after local verification.

## Bounded regression disposition and portable diagnostics

1. **Group failures by the first failing boundary.** Inspect the assertion, shared helper, runtime launcher, and fixture initialization before treating a large failure count as product defects. Reproduce one representative per failure family; rerunning the entire long suite before correcting a shared setup failure adds little evidence.
2. **Update only genuinely superseded expectations.** Trace the approved behavior to the new source output, replace the old assertion with an exact assertion for that behavior, and retain geometry, privacy, unused-row, revision, and decoder checks. An obsolete title assertion is not permission to loosen a whole scan test.
3. **Trace seed responsibility without bypassing auth.** If a synthetic account login fails, inspect whether the provider requires a persisted user and whether the launcher/global setup actually invokes the normal seed runner. On a verified isolated DB, compare fixture row presence before and after that runner. Repair setup ordering rather than minting fake authenticated state or relaxing account guards.
4. **Separate configuration from safety.** Reuse the project's app/provider port resolver and explicit test DB variable. Put evidence under a configurable directory with a repo-relative default, create that directory, and validate evidence filenames against traversal. Keep fixture UUIDs/dates deterministic when useful; do not hardcode personal checkout paths or test-server addresses into committed probes.
5. **Pin the actual mutation target.** Require an explicit loopback test DSN and project test namespace, reject known live/default targets, and compare actual datastore identity with an independently established test pin before writes. For PostgreSQL, obtain the cluster identity through `select system_identifier from pg_control_system()` when permissions allow it. Never derive the expected pin from the same unchecked target during the probe, because that makes the comparison tautological. Test missing configuration, non-test/remote targets, and a deliberately wrong pin; they must fail before mutation.
6. **Preserve evidence databases.** Give upgrade rehearsals unique validated names and refuse an existing target instead of silently dropping it. Run fixture-collision-prone SQL suites on a fresh prepared isolated DB, retaining earlier evidence rather than clearing shared state.
7. **Verify the bounded diff.** Format/lint explicit owned files, run affected unit tests and actual diagnostics where safe, then stage only those paths and use `git diff --cached --check && git commit ...`. If sibling work prevents a runtime rerun, label that path unverified instead of substituting prior results.
8. **Bind unchanged claims precisely.** For a test/probe-only repair, compare the relevant application/security paths against the verified base and record scoped content digests. Report that those bytes are unchanged, not that the newly changed harness or whole release is certified. Hand off exact SHA, changed files, commands/exits/counts, artifacts, setup root cause, and outstanding integration gates.
